从 chart-the-map 到 17 张票全部落地，把每一步真正绊倒过我的东西记下来。
17票 (13–29)
12次提交
269测试 / 0 失败
5篇 ADR
62+条 spec 决策
3次类型与服务器的矛盾被测量推翻

最重要的四条

如果只留四条，是这四条。其余都是它们的推论。

类型 ≠ 事实

我说的"plugin 无法枚举 session"是错的，而错因是我自己写的类型

我曾断言
session.list 不在 SessionDomain 的 Pick 里，所以插件不可能枚举 session，也就不可能知道"opencode 正在用哪个模型"。
真相
这话对 server plugin context 成立，对 TUI plugin context 不成立。它们是两个不同的类型。官方 @opencode/plugin/tui 的 Context 明写 data.session.list(): SessionInfo[] 和 client: OpenCodeClient，而 /goal命令面就是 TUI 插件。
为什么错
src/tui.tsx 里我手写的 TuiGoalContext 把 data.session 声明得比官方 SDK 窄。一个偏窄的类型让能力看起来不存在——于是我用"能力不存在"解释了一个本该去查的现象。
代价
用户连着两次报 403。第一次修复读 session.model，第二次才去枚举。
规则：一个类型是我写下的断言，不是世界的描述。当现象和断言冲突时，先怀疑断言——尤其是自己手写的那一份。
信封 ≠ 数组

session.list() 返回的是 {data: []}，我把它当成一行 push 了进去

现象
修完之后用户仍然 403。日志里 SESSION ... model=None——goal 记住了房间却没记住模型。
机制
生成客户端的签名是 (input?) => Promise<SessionsResponse>，而 SessionsResponse = {data: SessionInfo[], cursor}。我的代码把整个信封当成一个 row，于是 row.model 在包装对象上永远是 undefined，每个 session 看起来都没模型。
更讽刺的
用户的 step5 选择一直就在 opencode.db 里，同一个项目下，隔着一层信封。
规则："读到了但值是空的"和"没读到"要分开诊断。前者通常是形状不匹配，后者才是能力缺失——而这两者的修法完全相反。
测试会共谋

有测试把缺陷写成了契约，并且通过

实例 1
票 27 发现 /goal create 跑第 1 轮、autoStart 跑第 2 轮。而一个既有测试断言那第二轮是正确的——清空 prompts 后的 toBe(1) 量的正是这次双重踢。
实例 2
两个测试断言 roundsStarted === 0、零 prompt、以及那句"没有 session 打开"的提示——用户报的缺陷被原样写成了预期行为。
实例 3
一个测试的 includes('blocked') 匹配到了它自己 objective 里的词（"a goal that is never blocked"）。标记必须是精确短语 'Goal blocked ('。
规则：测试失败时先问"是这个测试错了，还是它保护的东西错了"。一个能通过的测试不等于一个说了真话的测试。
吞错会栽赃

plugin 的 try/catch 吞掉了测试自己的 ReferenceError，让测试 bug 伪装成能力缺失

现象
新测试失败在 madeWith[0] === undefined，看起来像"插件读不到模型"。
真相
mock 的 list() 闭包引用了一个未声明的自由变量，运行期抛 ReferenceError。插件的 try/catch——它是为了"surface 缺失不至于弄坏 /goal"而正确存在的——把它吞了，落到下一层。
推论
一个坏掉的测试和"能力不存在"长得一模一样。
规则：每一层静默失败，都让下面一层成为唯一证据。分层防御越完善，"证据在最后一层"这个陷阱就越深。

一、类型是对服务器的断言

这一类坑的成本最高，因为它让人停止调查。三次矛盾都是测量推翻的，没有一次是读代码读出来的。

已声明 · 未发布

session.viewed 在协议里声明了，从不发布

测量
三次成功的 POST /api/session/:id/view（200）→ 563 条记录事件里 0 条。session.* 家族只有两个 session.created。扫全部 563 个类型找 view/focus/open/active/select/enter/resume/load，一个都没有。
这是本 effort 第三次"类型与服务器矛盾"（前两次：票 25 的 inbox location、票 16 的扁平 SessionInfo.directory）。
设置 ≠ 解析

session.model 是"被显式设成什么"，不是"服务器解析成什么"

机制
默认解析发生在 prompt 时，且从不写回 session。插件自建的 session 没有 model 字段，读回来就是 undefined。
反证
opencode.db 里最近 25 个 session 有 24 个带 model——TUI 的 /model 确实持久化。缺口只在"plugin 自建的 session 没得可读"。
附带
session.update 不接受 model（协议里只有 title/permissions），但 session.switchModel 接受。所以旧房间只能被"修"，不能被"补"。
两种拼写

目录比较比的是同一条路径的两种写法

机制
session 行的 location.directory 用反斜杠，插件自己的 context.location.directory 用正斜杠。原始字符串比较把每一行都过滤掉。
这是同一个"什么都读不到"的第二条路。修了信封之后它仍然会让读取归零——两个独立的 bug，同一个症状。
可选性不一致

JSON body 不是 universally optional，也不是 uniformly required

  • session.create 接受 {}，不接受"无 body"（400）
  • session.view 拒绝 {}（Expected object），要求 {"idle": <epoch-ms>}
  • API 需要 Authorization: Basic base64("opencode:<password>")——裸密码 401，而密码只在启动时打印一次
提示词不带模型

续跑提示词的 payload 里根本没有 model 字段

测量
PromptInput.Prompt 只有 text/files/agents/skills；TUI 自己的调用是 {sessionID, text, files, agents, skills, delivery, gate, prepare}。模型是按 session 解析的。
后果
goal 跑在自己没记住的 session 里，就跑服务器默认值——而默认值可以是账号用不了的模型（403）。人类手打一句"1"能好，因为他们正走在 TUI 自己的路径上。

二、测试自己的错，长得像插件的错

这一类我全部记了下来，因为每一个都很容易用"弱化断言"糊弄过去。

四例

四个测试先错后对

  1. 复用测试根本没走到恢复路径。第一轮之后 ensureSession 已导航到那个 session，下一次 /goal 就复用了——这是正确行为，但不是要测的东西。必须先把路由放回 home，那才是恢复可达的状态。
  2. 替换测试把模型设在了 goal 从未用过的 session 上。它从 home 路由起步却把模型设在 ses-goal，而 home 起步会自建 session，所以 goal 正确地没记住模型，测试什么都没证明。
  3. run!('resume in the old room') 不是 resume。参数是 objective，动词必须是光秃秃的 resume。命令静默什么都没做——看起来像插件坏了。
  4. 要证明"房间还在但没模型"，房间必须存在且没模型。把它从 live map 里拿掉意味着"房间没了"，那是另一种情形、会正确地新建。测试断言错了那一边。
规则：测试因为自己的错误而失败时，最省事的修法是削弱它。每条这类记录都是为了那时候还能认出真相。
快照 vs 引用

mock 在构建时解构了引用，测试之后替换它就失效

机制
const {sessions} = harness 拿到的是快照。harness.sessions = [...] 换的是属性，解构出来的 const 还指着旧值。liveSessions 能工作只因为那是同一个 Map 的原地修改。
修法
改成可变盒子：collections.sessions，测试往里填。

三、机制必须被测量，不能被推断

四个假设里有三个被仪器化否掉。每一次"显而易见的原因"都是错的。

票 24

"完成前那一步的 token 永远丢失"——三个假设全错

假设 1
isGoalTurn 门挡掉了 → 否：四步都到了，没有守卫触发
假设 2
调用方过滤掉了 → 否
真相
GoalStore.addUsage 累进一个内存 overlay 且不落盘；overlay 搭下一次 mutation 走，而 commit() 会清掉它。现场数字：46,196 folded，22,839 记录（正好是步骤 1+2），complete 比步骤 3 早 12ms 盖章。
规则：仪器化要可移除且可证明已移除——用标记文件控制，然后用 dist/index.js 的 md5 与插桩前对比来证明行为保真。
票 22

"20ms 内 11 次 continue"——四个测量，前三个都排除了

  1. 执行事件是按 turn 不是按 step（2 步 / 1 成功）→ 排除
  2. 单 session 的 11 次爆发 → 1 轮准入，守卫没问题 → 排除
  3. 11 个子 session 爆发 → 0 轮，过滤有效 → 排除
  4. 一个事件扇出到两个 plugin 进程 → 2 轮准入。就是它。
级联
按 opencode 的提示词合并模型（回合中提交的提示词会打断当前回合，而打断本身又是一个回合完成事件），这个循环能自己跑自己——51ms 内 4 次 continue，每次 in=0 out=0，只被停顿守卫拦住。
缺的是所有权

轮询和定时器都不是答案

测量
session.viewed 从不发布；插件上下文无法枚举 session（server 侧）；plugin surface 里没有任何文件监视 API。
诊断
driver 的 in-flight 账是内存的且按 session 键控的，第二个进程看不到第一个进程的 round。缺的不是观察，是所有权。
规则：当"我希望能看到 X"反复出现时，先问"是谁该拥有 X"。看得见解不了一个没人负责的问题。

四、并发与状态

两个问题

"检测到变化"和"判断这是什么变化"必须是两个问题

坑
sync() 只比 goal 的 id/revision/phase。把 usage 加进去是必要的，但显而易见的版本是回归：applyExternalChange 结尾调 applyActivation，后者从 revision 算 mutatedWhileAlive。usage delta 不动 revision，于是一个 armed store 采用外部 delta 会读成"未在存活期间变更"从而自我解除。
修法
stateVerb 旗标——一个坐标不得触发状态动词的后果。
规则："东西变了"和"该为此做什么"耦合在一起时，加前者的检测会悄悄改后者的行为。
等待即阻碍

等路由变成 session 路由，就是在等 goal 存在的意义所要消除的那个行为

测量
在 opencode.exe 里：导航到 {type:"session", sessionID} 位于提示词提交处理函数内部（if (!i.sessionID) { ...; V.navigate(...) }）。所以 <leader>n 开的 session 会让路由停在 home，直到人类发送点什么。
修法
ensureSession() 自己造 session，而不是等它出现。且先建 session 再建 goal——反过来会让 server driver 的 session.created 和 TUI 命令面都准入第 1 轮。
坐标不是动词

租约、usage delta、session 记忆共用一条规则：不得 bump revision

规则
折叠给它们各自的槽位，永不进 goal 累加器、revision 或 lastRef；命名别的 goal 的行被丢弃；clear 一并清掉。
为什么
revision 是每个调用方持有的 ref 和 mutatedWhileAlive 读取的坐标。一次 usage 折叠不是状态动词，把它当动词会让每个 ref 变陈、让 armed store 自我解除。
代价：sync() 现在要比三样东西而不一样。少比任何一样，另一个进程的写入就无限期不可见。

五、部署与进程

插件在启动时加载

用户侧的 opencode.exe 是旧的，我改了文件也没用

诊断
每次都用进程启动时间和提交时间对比来排除"陈旧"这个解释——两次都是进程更新，于是确认是真 bug。
教训
"你更新了吗"是个真问题，但它不能被当成默认答案。先测量，再怀疑环境。
杀进程的顺序

kill_tree 必须先 taskkill /T /F 再 proc.kill()

机制
先杀父进程，taskkill 就只剩一个死 pid 可走，真正的 opencode.exe 会作为孤儿活下来——然后占着端口，让下一轮服务器起不来。
脚本改源码

用 Python heredoc 编辑源码吃掉了 150 行 GoalAccounting

机制
一个"还原"脚本匹配失败后仍执行了替换。文件未被 git 跟踪，无法 git checkout 恢复。
恢复
从编译过但未压缩的 dist/index.js 打包产物加早先的 read 输出，手工重建类体；然后 typecheck、全测试、dist md5 一致来证明还原正确。
同类
三引号 Python 字符串里的 \n 会静默变成真换行，破坏精确匹配补丁。带空格的路径打断 inline heredoc——写脚本文件，别 inline。
规则：对源码的机械编辑，锚点文本必须精确，且优先用编辑工具而不是脚本。
静默失败链

插件不加载的四层原因，我前三层都猜错了

  1. 猜"语法错误"→ bun build 通过，否
  2. 真相：JS 里 \U 不是语法错误，它就是 U。路径变成 C:Users/...，写文件时 ENOENT 抛出
  3. 猜"项目级 .opencode/plugins 在 serve 里不加载"→ 否
  4. 真相：默认导出必须是 {id, setup} 对象。我导出的是一个函数
这条链本身是个教训：四层静默失败，我用"提升到全局安装"绕过了三层，仍然没找到真因。真正的突破来自去读 Plugin.Plugin 的类型定义。
写进被操作的目录

把脚本写进它操作的目录，造出了 issues/issues/ 双重嵌套

规则
产出物和输入分开目录。特别是脚本自己要创建目标目录时。

六、过程

低于地板的 verdict

Jev 给出 0.59、0.43、0.49 的时候，记下来而不是反复重问到它过线

原则
每次重问都连同原分数一起记录。票 26 的 0.59（放置位置）重问后 0.81；票 27 的 0.43（日志可读性）从未过线，也留在票里。
规则：逐个地板分重问到过线，和"根本没记录"是同一个动作。
票界纪律

重构票里不做顺手的行为修改

做法
每个缺陷开自己的票。于是本轮从 2 张用户报的缺陷长出票 28、29——每张都可独立 review，每个都可被单独证明在 HEAD 上失败。
代价是票数变多。收益是"这一版到底改了什么"永远有唯一答案。
诚实报告

三次我选择把难看的证据写进去

  1. 验收跑只跑了一轮。 before/after 各一次，就写在票里，没有抹平。
  2. 字面意义上的"延迟"从未出现。票 27 的活体验证里，第一个进程的 round 在第二个进程的 turn 落地前就完成了 goal。我记录了这一点，外加证明第二个进程的 turn 确实跑过的诊断。
  3. 10 个 stops 测试不能算"在 HEAD 上失败"。它们 import 的新 API 在 HEAD 不存在，所以整个文件加载失败而非断言失败。这不是同一种证据，我没把它当成。真正的证据是用户自己日志里那条 usage-limited + provider.transport。
规则：把证据换成更强的那一种很容易，把证据诚实分类才让结论可用。
